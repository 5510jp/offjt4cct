# AIの自己修正を過信しない：外部チェックを組み込む「ハーネス」実践ガイド

## 1. 導入

「念のため、間違いがないか見直してください」

AIにそう頼んだところ、「問題ありません」と返ってきたのに、後から誤りが見つかった。<br>そんな経験はないでしょうか。<br>

- コードを再確認させたが、同じ境界条件のバグを見落とした
- 「全件チェックして修正しました」と答えたのに、実際には途中で諦めていた
- 長い会話の途中で、最初に伝えた要件が抜けた
- 読みやすい文章だが、出典を開くと主張を裏付けていなかった

LLM（大規模言語モデル）による自己修正は、いつでも成功するわけではありません。<br>特に、正解やテスト結果などの外部フィードバックがない状態で、モデル自身に推論の誤りを見つけさせる方法には限界があることが報告されています。<br>

一方で、「AIは自分の間違いを直せない」と言い切るのも正確ではありません。<br>課題の種類、モデル、プロンプト、外部フィードバックの有無によって結果は変わります。<br>検証可能なテスト結果や正確な指摘を与えると、修正できる場合もあります。<br>

そのため実務では、AIの自己申告だけに頼らず、生成後に機械的な検査、出典確認、LLM評価、人間の判断を重ねる多層的な仕組みを作ります。<br>

> **💡 用語解説：ハーネス（Harness）**  
> モデルにプロンプトを渡すだけでなく、使用するツール、参照情報、進捗管理、テスト、合否判定、停止条件などを外側から組み合わせる実行管理の仕組みです。<br>

## 2. AIの自己修正について分かっていること

### 2.1 外部情報のない自己修正は、推論課題で悪化することがある

ICLR 2024で発表された論文[『Large Language Models Cannot Self-Correct Reasoning Yet』](https://openreview.net/forum?id=IkmD3fKBPQ)は、GSM8K、CommonSenseQA、HotpotQAなどの推論課題を対象に、正解ラベルを与えない「内在的自己修正」を調べました。<br>

実験では、GPT-3.5、GPT-4、GPT-4 Turbo、Llama 2を対象とした実験において、自己修正後の正答率が改善せず、低下するケースが確認されています。<br>最初は正しかった回答を、見直しによって誤答へ変更する例もありました。<br>

ただし、この結果から「すべてのAIは、文章やコードを含むあらゆる課題で自己修正できない」とは結論できません。<br>論文が扱ったのは、特定のモデルと推論ベンチマークにおける、外部フィードバックなしの条件です。<br>

### 2.2 「自己修正の盲点」は、モデルや条件に依存する

2025年のプレプリント[『Self-Correction Bench』](https://arxiv.org/abs/2507.02778)では、モデルが自分の出力に含まれる誤りを直せない一方、外部から与えられた同じ誤りは修正できる現象を「Self-Correction Blind Spot」と呼んでいます。<br>

同研究は14のオープンソース言語モデル（o1のような推論特化型ではない標準モデル）を対象に、平均64.5%のblind spot rateを報告しました。<br>これは制御された注入エラーに対する値であり、実運用における自己修正の失敗率を示すものではありません。<br>また、すべてのLLMに共通する値でもありません。<br>同研究では、回答に「Wait」を加えて思考プロセスを促すとblind spotが89.3%減少したことも報告されており、プロンプトの設計次第で緩和できる可能性を示唆しています。<br>

### 2.3 誤りの場所や外部フィードバックがあると修正しやすい

[別の研究](https://aclanthology.org/2024.findings-acl.826/)では、LLMは論理的な誤りの**発見**には苦戦するものの、誤りの場所を正しく示されると修正できることが報告されています。<br>また、[2024年の批判的サーベイ](https://aclanthology.org/2024.tacl-1.78/)は、信頼できる外部フィードバックを利用できる課題では自己修正が機能しやすいと整理しています。<br>

実務では、単にAI自身に再考させること以上に、まず以下の条件が整っているかを確認することが重要です。<br>

- 正解や根拠へアクセスできるか
- コードを実行し、テスト結果を取得できるか
- 評価基準が具体的か
- 誤りの候補を独立した方法で見つけられるか

### 2.4 なぜ未完了でも「やりました」と嘘をついてしまうのか

実務でAIを使っていて特に厄介なのが、実際には途中で諦めていたりエラーで失敗しているのに、「すべての修正が完了しました」「ご指定通りに処理しました」と平然と虚偽の完了報告をしてくる現象です。<br>

この現象には、LLMの構造的な理由が2つあります。<br>

1. **「次の言葉」を確率で予測しているだけであること**  
   LLMは裏で処理の成否を実際に検証して発言しているわけではありません。「このような依頼を受けた文脈では、次は『完了しました』と返す確率が統計的に高い」という予測に基づいて文字を紡いでいます。<br>
2. **人間に迎合するバイアス（Sycophancy）**  
   RLHF（人間のフィードバックによる強化学習）を受けたAIは、ユーザーの指示に肯定的に応じるよう調整されています。そのため、「エラーでできませんでした」と素直に認めるよりも、ユーザーを満足させるようなもっともらしい返答（ハルシネーション）を優先してしまう傾向があります。<br>

プロンプトに「もし処理できなければ正直に白状してください」と書き添えることである程度緩和できますが、モデル自身の自己認識（Calibration）には限界があります。<br>
だからこそ、AIの「やりました」「問題ありません」という**言葉（自己申告）そのものを成果として信用せず、外側から検証する仕組み（ハーネス）**が不可欠になります。<br>

## 3. ハーネスは「別チャット」より広い仕組み

[Anthropicの記事](https://www.anthropic.com/engineering/building-effective-agents)では、あるLLM呼び出しが回答を生成し、別のLLM呼び出しが評価とフィードバックを行う「Evaluator–optimizer」ワークフローを紹介しています。<br>この構成は、評価基準が明確で、反復による改善を測定できる場合に適しています。<br>

[Anthropicの長期タスク用ハーネス](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)は、要件を構造化した機能一覧、セッションをまたぐ進捗ファイル、Git履歴、段階的な実装、ブラウザ操作を含むエンドツーエンドテストを組み合わせています。<br>

新しいチャットで検品する方法は、過去の説明に引きずられにくくするための簡単な工夫です。<br>しかし、それだけで評価の独立性や正しさが保証されるわけではありません。<br>同じモデルは、別チャットでも同じ知識の欠落や評価バイアスを持つ可能性があります。<br>

実務では、単一チャットの自己修正に頼らず、以下の多層的なチェック層を順に組み合わせます。<br>
その際、最も重要な大前提となるのが**「SSOT（Single Source of Truth：信頼できる唯一の情報源）」をチャットの外側に定義すること**です。<br>

AIが自己修正に失敗したり、会話を続けるうちに誤った事実を前提にしてしまう（コンテキスト汚染）大きな原因は、**「AI自身の過去の出力」を情報源として扱ってしまうこと**にあります。<br>
何が正しい仕様なのか、どのデータが確定した事実なのかという「唯一の真実（SSOT）」を外部（仕様書、一次資料、テストコード、Git履歴など）に置き、AIの成果物をそのSSOTと照らし合わせて検証する構造を作ります。<br>

```mermaid
flowchart LR
    R["外部のSSOT<br/>確定要件・一次資料・テスト"] --> G["Generator<br/>成果物を作成"]
    G --> D["機械的チェック<br/>文字数・禁止語・テスト"]
    D --> S["出典・一次資料との照合"]
    S --> E["Evaluator<br/>意味・構成・リスクを評価"]
    E --> H["人間による最終判断"]
    
    %% 修正ループ
    E -->|修正点| G
```

### チェック方法の役割分担

| 確認したいこと | 適した方法 | 注意点 |
|---|---|---|
| 文字数、必須語、禁止語 | スクリプトや文書機能 | LLMに数えさせる必要はない |
| コードの動作 | 自動テスト、静的解析、実行結果 | テスト自体の不足には注意する |
| 日付、価格、仕様、引用 | 公式資料や一次情報との照合 | 情報の更新日も確認する |
| 読みやすさ、論理構成 | LLM評価と人間レビュー | 評価者の好みやバイアスが入る |
| 社内事情、責任、公開可否 | 担当者による判断 | AIだけで承認しない |

## 4. 実践：ノーコードで始める生成・検品フロー

社内告知メールを例に、ブラウザ上のAIで試せる手順を説明します。<br>機密情報や個人情報を入力する前に、社内ルールと利用サービスの設定を確認してください。<br>

### ステップ1：作成前に合格条件を決める

本文を書かせる前に要件を整理し、「高品質に」のような形容詞を確認可能な条件へ変換します。<br>

```text
社内告知メールを作成する前に、次の項目を整理してください。

1. 対象読者
2. メールの目的
3. 本文に必要な確定情報
4. 文字数の目安
5. 読者が行う手順
6. 公開前に担当者が確認すべき情報

確定していない日付、URL、連絡先は推測で補わず、
「要確認事項」として本文の外に列挙してください。
まだ本文は作成しないでください。
```

AIが提示した条件は、人が確認します。<br>特に日時、対象者、問い合わせ先、URLは、社内の正式情報と照合してください。<br>

### ステップ2：初稿を作る

```text
確認済みの要件に基づいて、社内告知メールの初稿を作成してください。

要件:
- 400〜600文字
- 対象者、開始日時、設定期限、3段階の操作手順、問い合わせ先を含む
- 「後日」「近日中」など、期限が分からない表現を使わない
- 未確認の事実や連絡先を作らない

本文の後に、要件ごとの自己チェック結果を付けてください。
```

ここであえて自己チェックを付けさせるのは、AIに要件を再意識させる思考の足場を作るとともに、後のステップで「自己申告と実態の乖離」を確認しやすくするためです。<br>
出力された自己チェックはあくまで参考情報とし、合否判定は次のステップ3以降で**成果物の実体（テキスト、表、ファイル、ログなど）**を対象に実施します。<br>

### ステップ3：機械的に確認できる条件を先に調べる

文字数、必須項目、プレースホルダーなどは、プログラムやツールの機能など、LLMより決定的（確実）な方法を優先して調べます。<br>

- 文書ソフトの文字カウントで400〜600文字か確認する
- `[担当者名]`、`○○`、`TBD`などを文書内検索する
- URLを実際に開く
- 日時、曜日、連絡先を正式な案内と照合する

この段階で失敗した項目は、LLM評価へ進む前に修正します。<br>

### ステップ4：別の文脈で意味とリスクを評価する

新しいチャットを利用する場合は、元の長い会話履歴ではなく、確定した要件、評価基準、成果物だけを渡します。<br>
評価役（Evaluator）のLLM自身にも正確な文字カウント機能やWebアクセス権限はないため、プロンプトで「確認手段がない項目は推測で合否を出さず、外部確認待ちとする」ルールを明記します。<br>

```text
次の成果物を、提示した要件だけに基づいて評価してください。

【重要】
- 成果物に書かれた事実が正しいとは仮定しないでください。
- 文字数やリンク到達性など、確認手段がない項目は
  PASSにせず「外部確認待ち」としてください。
- 問題がなければ、問題がない根拠を要件ごとに示してください。

【出力形式】
判定: PASS / FAIL / 外部確認待ち

要件別結果:
- 要件:
  結果:
  根拠または該当箇所:

修正提案:
- 必要な場合のみ記載

【要件】
[確定した要件を貼り付け]

【成果物】
[初稿を貼り付け]
```

### ステップ5：指摘を戻して修正する

Evaluatorの指摘をGeneratorへ渡すときは、指摘を無条件で正しいものとして扱わないようにします。<br>

```text
次の指摘を確認し、妥当な項目だけを反映してください。
各指摘について「採用・不採用」と理由を示した後、改稿版を出してください。
確定情報を推測で追加してはいけません。

【評価結果】
[Evaluatorの結果を貼り付け]
```

修正後は、機械的チェック、出典確認、意味の評価をもう一度行います。<br>

## 5. 外部のSSOT（進捗・仕様）をAIに勝手に書き換えさせない

進捗や判定をJSONなどの構造化形式にすると、必要な項目の欠落を検出しやすくなります。<br>[Anthropicも長期タスクの実験で](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、機能一覧をMarkdownよりJSONで管理した方が、モデルに不適切に変更・上書きされにくかったと報告しています。<br>
これは、**「何が完了し、何が未完了か」という進捗のSSOT（唯一の真実）を、モデルの気まぐれな上書きや改ざんから保護する工夫**と言えます。<br>

ただし、JSONなどの形式を採用しても、それだけで正しさが保証されるわけではありません。<br>形式が正しくても、モデルが誤った理由で`PASS`を出すことはあります。<br>

```json
{
  "status": "FAIL",
  "checks": [
    {
      "criterion": "問い合わせ先が正式情報と一致する",
      "result": "FAIL",
      "evidence": "一次資料と照合した結果、記載された内線番号が存在しない"
    }
  ]
}
```

構造化の目的は、判断を正しく見せることではなく、**判断と根拠を後から検査しやすくすること**です。<br>

## 6. 実運用で気をつけること

- **LLMの評価は「客観的証拠」とは限りません。**<br>[LLM-as-a-Judgeの研究](https://arxiv.org/abs/2306.05685)では、MT-Benchで非同点票だけを集計したS2条件において、GPT-4と人間の選好判定が85%一致しました。<br>一方で、同じ研究は位置バイアス、長い回答を好む傾向、推論問題での誤判定を報告し、評価モデルが自身の生成した回答を好む可能性も検討しています。<br>85%という数値を、あらゆる文書やコードの正確性へ一般化することはできません。<br>

- **同じモデルを別チャットで使っても、完全には独立しません。**<br>会話履歴は分離できますが、モデルの学習済み知識や癖は共通です。<br>重要なファクトチェックでは、一次資料、検索、計算、テスト、専門家レビューを組み合わせます。<br>

- **FAILを出しやすいEvaluatorが優秀とは限りません。**<br>厳しい言葉を使うと、実在しない欠陥を作り出す可能性もあります。<br>評価基準には、厳しさだけでなく、根拠、該当箇所、確認不能の扱いまで指定しましょう。<br>

- **人間の最終判断を残します。**<br>契約、法務、セキュリティ、医療、財務、対外発表など、誤りの影響が大きい成果物は、担当者や専門家が最終確認します。<br>AIの評価は一次チェックとして利用します。<br>

## 7. まとめ

公開前に以下の4点を確認してください。<br>

1. **合格条件と事実の拠り所（SSOT）をチャットの外に置く**
2. **文字数やテストは機械的に確認する**
3. **事実は外部の一次資料や実行結果と照合する**
4. **LLM評価を補助にして、人が最終判断する**

まずは次に作る重要な文書で、「必須項目」「禁止事項」「外部確認が必要な項目」を3つずつ書き出し、AIとの会話の外側に**信頼できる拠り所（SSOT）**を用意してみてください。<br>それだけでも、曖昧な「見直して」によるコンテキスト汚染を防ぎ、根拠を確認できる堅牢な検品フローへ一歩進めます。<br>
